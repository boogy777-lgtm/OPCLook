# Рефакторинг: текущая матрица

Исходные предложения и находки приведены в [плане](refactoring-plan.md). Ниже — итог реализации; записи в [devlog](devlog.md) и [аудите](audit-2026-10-27.md) являются историей отдельных ревизий.

| Тема | Реализация и свидетельство |
|---|---|
| A: типы и роли | Ненулевые `SessionId`, `RequestId`, `ScanId` и `ItemKey`, `Owner::Discovery/Session`, `Origin::Reply/Unsolicited`, типы качества, VT и сетевых индексов заменяют неоднозначные значения. Корреляция и проверки исчерпания покрыты тестами contract и Engine. |
| B: состояния | Типизированы pane, identity и поиск UA, исход scan, DA hit, lifecycle CSV и helper, вид сессии и сообщение журнала. Подтверждение содержит обязательное действие. Headless тесты проверяют переходы и взаимодействия. |
| C: границы входа | Настройки и endpoint разбираются в типы с совместимостью старого JSON; ограничения применяются при загрузке. UA URL разбирается централизованно; интервалы и дедлайны представлены `Duration`. Тесты проверяют миграцию и некорректный ввод. |
| D: ресурсы | COM и WinAPI ресурсы защищены владельцами и cleanup; проверяются null и layout массивов, ограничена вложенность. Тесты ресурсных путей включают Windows-only проверки; локально Windows проверен по типам. |
| E: ошибки | Typed send, UA service, helper IPC, shutdown и настройки сохраняют причины; UI локализует сообщения. CSV сообщает номера строк и ограничивает число диагностик. B15 проверен через живой sample и proxy с production deadline. |
| F: кадр | Кэши строк и дерева, ограниченный обход значений и виртуализация журнала сокращают работу кадра. Измерения, условия и отдельный рост числа аллокаций в сцене обновления — в [отчёте](reports/refactor-frame-baseline.md). |
| G: коллекции | Индексы и множества заменяют повторные линейные поиски; UA хранит разобранные NodeId и индекс мониторов. Регрессии и live UA проверяют изменения. |
| H: структура | Contract разделён по доменам; backend выделяет network и UA session модули; GUI `App` координирует обработчики событий, `WriteBatch` и компоненты UI. Settings группируются с плоской serde-совместимостью. Границы зависимостей и compile-fail тесты проверяют закрытость Gateway. |

`PendingRequests` и удержание DA-маршрутов принадлежат Engine; сеть уже организована в `NetworkState`. Дополнительные одноимённые структуры в GUI не нужны. Общий modal-каркас был необязательным предложением, а Protocol trait, DI и EventBus не требуются для существующих границ.

## Проверки и границы

На Linux `scripts/check-linux.sh` завершился успешно для кода `c5762583f96635b37bc8924295703fde9bdccc8b`; до миграции на Rust 1.99 последующие коммиты изменяли только документацию. Backend: 218, включая live UA и два B15 proxy-теста; CLI: 6 unit и 2 live; contract: 29 и 3 doctest; Engine: 23 и 2 doctest; locale: 11; GUI: 219 library, 149 interactions (один Windows-only ignored), table 20, navigation 16, theme 14. Два B15 теста используют реальный 30-секундный deadline и вместе занимают около минуты. После очистки кэша GUI повторно прошли all-target check, обычная сборка GUI/CLI и все GUI test targets.

Rust 1.95.0 выполнил `--locked --offline` Windows i686 workspace all-targets typecheck с test-only пропуском GUI ресурсов и helper manifest; Windows при этом не исполнялась. Native Windows unit tests предусмотрены CI. Полный CI был зелёным для `72a208504df2db7116f98d4af79e645dc6b9404f` (run `40713447892`) и `237e0bf` (run `40718289923`). Состояние последнего HEAD — в [PR #8 checks](https://github.com/boogy777-lgtm/OPCLook/pull/8/checks); merge требует зелёных проверок точного HEAD. Эти проверки не доказывают работу на физическом DA-сервере, UAC, привилегированном helper или реальном маршруте.

Пять сцен App отрендерены и просмотрены до F, после F и после H; fixture helper не является реальным IPC. CPU baseline и результаты после F получены на Linux в инструментированном оптимизированном test profile, не в Windows release и не как GPU FPS или живая память. В сцене 100 обновлений число аллокаций выросло на 36 (+0,8%), хотя время и запрошенные байты снизились.

Engine фильтрует поздние unsolicited данные, пока сессия отключена или подключается. После нового соединения старые unsolicited события не содержат эпоху соединения, поэтому их происхождение не всегда можно определить; наличие такого события после переподключения не заявлено как воспроизведённый дефект.
