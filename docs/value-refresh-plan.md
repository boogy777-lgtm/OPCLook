## 1. Основание по правилам 3.1

- **Class:** потребность получить значение зарегистрированного ItemKey текущей
  эпохи подключения. Browse и поиск серверов находятся вне класса.
- **Inv:** потребность завершается соответствующим ответом, явной ошибкой или
  отменой; завершение старого запроса не уничтожает новую потребность.
- **N+1:** новый повод обновления использует существующие очередь, корреляцию,
  ограничение нагрузки и планировщик. GUI и CLI не создают отдельных механизмов.
- **Defect/guard:** проверить AddItems, Write, Poll, Refresh, reconnect и Remove;
  детерминированные тесты перестановок событий защищают от повторения класса.

Не строить универсальный EventBus или новый слой команд. Расширить существующие
`Engine::accept`, `Engine::due`, корреляцию `RequestId` и проверку эпох Connect.
Исправление resize из #15 остаётся локальным использованием TableBuilder.

Документация PTC описывает Kepware в роли UA-клиента к другому UA-серверу.
Она не доказывает способ внутренней реализации каждого драйвера Kepware или
свойства обновления физического ПЛК за произвольным сервером.
Запрет протокола на совместное использование Read и Subscription не установлен:
PTC сам документирует разовое восстановительное чтение при подписке.

## 3. Инженерный компромисс OPCLook

У сессии ровно одна выбранная политика постоянного получения данных.
Разовые диагностические чтения имеют отдельную цель и не создают второй цикл.

| Политика | Постоянный канал | Разовые чтения | При отказе канала |
| --- | --- | --- | --- |
| Subscription, рекомендуемый режим UA | MonitoredItems / Publish. Периодического Read значений нет. | Начальный снимок при отсутствии результата, восстановление снимка, чтение после Write Ok и явный Refresh. | Показать Failed/Degraded и затронутые ключи. Не включать скрытый polling. |
| Poll | Пакетный Read по интервалу Engine. Для этих значений нет активных MonitoredItems. | Выполняются через тот же планировщик и объединяются с ближайшим ещё не отправленным подходящим чтением. | Показать ошибку чтения/сессии; не создавать подписку автоматически. |

Это рабочее решение для реализации, а не утверждение о текущих возможностях.
Переключение Subscription/Poll должно быть явным и видно пользователю.
При переходе остановить старый канал и отменить его отложенную работу до запуска
нового. Доставка запоздалых событий не должна менять новую политику.
Для DA использовать тот же AcquisitionConfig в EndpointSpec: UpdateMode и
разовые потребности общие. COM Sync/Async, Cache/Device и callback lifetime
реализует адаптер. [Спецификация соединения](connection-acquisition.md) задаёт
capability-проверки и исключает отдельный DA-планировщик.

Текущие `poll_only` и автоматический polling при Inactive/Failed допускают
деградацию, но нарушают чистоту диагностического режима. На этапе R2.3 убрать
скрытую подмену: неподдержанные MonitoredItems остаются видимыми как проблема;
пользователь может явно выбрать Poll для сессии либо отдельную Poll-сессию.
Один и тот же набор тегов не обслуживается двумя постоянными каналами.

Не считать отсутствие DataChange признаком неисправности, если значение постоянно.
Контролировать жизнеспособность подписки по её состоянию, Publish/keepalive и
ошибкам протокола. Разовый Read, давший значение, не доказывает работу подписки.
Показывать выбранную политику, состояние канала и источник последнего результата
(Read или Subscription), чтобы снимок не маскировал дефект потока.

### Начальный снимок и reconnect

После успешного AddItems создать потребность начального снимка в Engine.
В Subscription сначала принять начальное уведомление; если снимка нет после
одного пересмотренного publishing interval, поставить недостающие ключи на
одно разовое чтение. Это стартовое правило OPCLook по аналогии с восстановлением
Kepware, а не нормативный срок начальной доставки OPC UA. При медленном источнике
не объявлять сервер несоответствующим стандарту только по истечении этого срока.

Учитывать пересмотренные сервером интервалы; если backend их не передаёт,
сначала расширить контракт. Обработать уведомления, пришедшие до AddItems reply:
не создавать повторную начальную потребность для уже полученного результата
той же регистрации и эпохи. Bad_WaitingForInitialData остаётся ожиданием;
конечный Bad-статус является явным результатом, а не успешным значением.

При явном reconnect со сменой локальной Connect epoch снять старую работу.
Краткое восстановление SecureChannel библиотекой не тождественно новой эпохе
или новой remote Session. Recovery/replay сначала проверяется у SDK-владельца;
при создании remote Session/Subscription обновляются adapter registrations/aliases.
При новой регистрации снова применить начальный снимок. При сохранённой подписке
запросить недостающий снимок по реальному recovery outcome. Невосстановленный
history gap не исчезает от получения текущего снимка.
Не включать бесконечное периодическое чтение при отсутствии push.

### После записи

Только коррелированный Wrote Ok создаёт потребность чтения записанного ключа.
Read для этой потребности отправляется после подтверждения Write.
Ранее отправленное чтение и произвольное push-уведомление её не удовлетворяют.
Несколько записей до отправки объединяются по ключам. Ошибка Write не подставляет
в таблицу запрошенное пользователем значение.

Различать «запись принята», «сервер вернул наблюдаемое значение» и «наблюдаемое
значение совпало с запрошенным». Read-back не доказывает выполнение ПЛК-логики
или физическое действие исполнительного механизма.

## 4. Общий механизм в Engine

Представление состояния уточнить при реализации без дублирования владельцев:

- `pending_refresh` содержит ожидающие ключи и минимальные данные цели:
  InitialSnapshot, WriteReadback или ExplicitRefresh, а также срок допуска.
  Периодический Poll добавляет потребность только при выбранной политике Poll.
- Отправленный Read в существующей таблице запросов хранит RequestId, эпоху,
  состав ключей и покрытые потребности. Не строить вторую таблицу корреляции.
- При отправке ожидающие потребности переходят в этот запрос. Новая потребность
  того же ключа, созданная во время Read, остаётся в pending_refresh.
- Ответ, Error и timeout завершают только свой запрос и покрытые им потребности.
  Не применять `pending_refresh.clear()` к сессии.
- Push может закрыть ещё не отправленную InitialSnapshot-потребность этой
  регистрации. Push не освобождает слот выполняющегося Read и не закрывает
  WriteReadback. Это различие определяется целью, а не местом вызова в UI.
- Для отсутствующего в ответе ключа и плохого результата сформировать явный
  исход. Не считать частичный ответ успехом для всей пачки.
- Ошибка завершает попытку с диагностикой. Не создавать неограниченный retry.
  Новые потребности обслуживаются только работоспособным транспортом. UA IO timeout
  может quarantine сессию: сначала закрыть её работу, затем восстановить регистрацию.
  Не повторять Write автоматически при unknown outcome.
- Remove отменяет потребности ключа и исключает применение его старых ответов.
  Disconnect/смена эпохи/политики отменяют относящуюся к ним работу.

Все автоматические чтения и явный Refresh проходят один путь Engine.
App не создаёт Read после AddItems/Write и не решает, какие ключи надо перечитать.
Низкоуровневый send не должен позволять обойти ограничение нагрузки Read.
Коррелированный одиночный Read CLI использует тот же слот; сохранить его
понятный результат и не подменять выполнение команды фоновым push.

Допускается не более одного логического Read в работе на сессию.
Большой набор разделяется на ограниченные транспортные пачки существующим
backend-механизмом. Между сессиями остаётся независимое обслуживание.
Новые потребности не ждут следующего polling interval: их ограничивают только
слот, допустимое время и общий арбитраж.

Browse и Read не перекрывать в пределах существующего ограничения.
Обеспечить отсутствие голодания: перед отправкой следующей пачки рекурсивного
Browse дать просроченному Refresh слот на безопасной границе. Проверять
очередность детерминированным временем, не придумывать измеренный предел задержки.

### Возраст данных

Сейчас `crates/backend/src/bff/ua/io.rs::read` использует
`read_values_chunked(..., TimestampsToReturn::Both, 0.0)`.
Не описывать это как гарантированное чтение из кэша.

В контракте чтения явно задать допустимый возраст: для начального/восстановительного
снимка использовать пересмотренный publishing interval; для WriteReadback и
явного Refresh запросить maxAge=0. При объединении потребностей выбрать более
строгое требование. Это проектная политика OPCLook; best effort и статус сервера
остаются видны, абсолютная свежесть физического источника не обещается.

## 5. Временные метки (#14)

Хранить отдельно source_timestamp, server_timestamp и локальное received_at.
Последнее не подставляется в поля временных меток сервера.

Для совместимости основной ячейки сохранить source.or(server), но показывать
происхождение времени. Подробности должны предоставлять обе исходные метки.
ServerTimestamp нельзя без пояснения подписывать «время изменения источника».
При отсутствии обеих меток показывать отсутствие, не придумывать серверное время.
Не переносить метку старого значения на новый результат без метки.

Каждый принятый актуальный результат может обновить метки даже при равном
значении. Локальное changed_at для подсветки изменения остаётся отдельным.
Полученное позже уведомление подписки проходит тот же путь обновления.
Не сравнивать SourceTimestamp и ServerTimestamp как одну общую шкалу версий.

В текущем коде события применяются по поступлению; гарантии отсутствия регресса
между снимком Read и очередью Publish нет. Для реализации проверить перестановки:
при сравнимых SourceTimestamp одной эпохи не заменять более новый экземпляр
старым; результат своей операции Read при этом завершить отдельно от решения
о замене отображаемого значения. При несравнимых/отсутствующих метках сохранить
явное происхождение и порядок получения, не объявлять физическую новизну доказанной.
Не вводить глобальный порядок между разными серверами по UTC.

## 7. Приёмка

Нормативные условия: [R2.TEST](testing/acquisition-truth-tables.md).
Полные CSV G/D покрывают по 128 булевых комбинаций; дополнительно обязательны
таблицы переходов E/S/T, конфигурации C/U/M и адаптерные A. Число строк данных
не является числом пройденных тестов. Проверять реальные entry points.

- [ ] Add/Write/Poll/Refresh объединяются без обходов Engine и двойных Read.
- [ ] Read A → Wrote Ok(A) → ответ старого Read не удаляет новый read-back.
- [ ] Новая потребность во время Read переживает его Error/timeout.
- [ ] Push не освобождает Read-слот и не подтверждает запись.
- [ ] Ранний push до AddItems reply не вызывает лишний начальный snapshot.
- [ ] В Subscription разовый fallback не скрывает сломанную подписку.
- [ ] В Poll нет monitored values и второго постоянного канала.
- [ ] Inactive/Failed/poll_only не включают скрытую смену политики.
- [ ] Remove/reconnect/смена режима отвергают старую работу и поздние результаты.
- [ ] Частичные ответы, Bad и отсутствие времени видны пользователю.
- [ ] Обе временные метки сохраняются; равное значение допускает обновление времени.
- [ ] Проверены старый Read после нового push и старый push после нового Read;
      завершение операции не зависит от применения результата к текущей строке.
- [ ] Длинный Browse не блокирует Refresh бессрочно; другая сессия обслуживается.
- [ ] maxAge передаётся согласно цели и не выдаётся за гарантию физической свежести.
- [ ] GUI и CLI проверены на одной семантике Engine.
- [ ] Live UA: начальное уведомление, задержка/отсутствие push, write-readback,
      reconnect, ошибки; затем внешний CODESYS и физический Windows/DA стенд.
- [ ] После изменения кода: fmt, целевые тесты, Linux и native Windows проверки
      точного HEAD; обновить status/devlog/audit. Не переносить старые результаты.
