# План: выбор сетевой карты, LDS/mDNS и поиск OPC UA в сети

**Статус:** этапы 1–8 реализованы в коде (2026-10-26). Живая проверка DA на втором
хосте и ручная проверка helper под UAC остаются заблокированными средой (нет
Kepware/второго DA-хоста).  
**Проект:** `opcda-egui`  
**Область:** OPC UA discovery, сканирование подсети, привязка UA-трафика к адаптеру, DA route steering.

> **Актуальная семантика выбора адаптера:** `docs/plan-ua-search-network.md`
> новее и отменяет `AdapterSelection::Auto`, автоматический выбор и fallback.
> В коде реализованы `None | Adapter(GUID)`, один ComboBox, без молчаливого
> fallback. Loopback-операции разрешены без выбора адаптера; удалённые
> операции и подсеть требуют явного адаптера. Пункты ниже, описывающие
> `Auto`/fallback, сохранены как история решения и не отражают текущий код.

## 1. Цель

Добавить в popup OPC UA:

- кнопку **«Поиск через LDS/mDNS»** — штатное обнаружение серверов;
- кнопку **«Поиск в сети»** — loopback + N адресов подсети выбранного адаптера;
- вкладку **«Сетевые настройки»** — выбор карты, сохранение, fallback;
- привязку всего UA-трафика к выбранной карте;
- отдельный механизм для DA, не смешанный с UA;
- лимит 100 UA-сессий.

## 2. Утверждённые решения

| Вопрос | Решение |
|---|---|
| Ручной выбор карты | Любая: физическая, виртуальная, VPN |
| Fallback | Только физический адаптер; выбор один раз на lease |
| Сохранение | GUID адаптера; IP и ifindex определяются заново |
| DNS | Системный резолвер; привязывается TCP-соединение |
| Область поиска | IP + маска выбранной карты |
| Большие подсети | Порог 4096 адресов; больше — подтверждение и сужение CIDR |
| N+1 | N адресов подсети + loopback; loopback всегда первый |
| Параллельность сканера | FIFO, до 32 одновременных проверок |
| LIFO | Не используется |
| Автозапуск поиска | Нет; только по кнопке |
| Лимит сессий | 100 UA-сессий; константа, не хардкод |
| DA | Полная реализация через привилегированный helper |
| WFP-драйвер | Не используется |

## 4. Архитектура

```text
AdapterSelection (settings.json)
        │
        ▼
NetworkLease — неизменяемый снимок
GUID, ifindex, LUID, IP, prefix, subnet, generation
        │
        ├── UA BoundConnectorFactory
        │     ├── N сессий            свой TCP-сокет
        │     ├── LDS                свой TCP-сокет
        │     ├── mDNS               InterfaceIndex
        │     └── Scan pool (32)     свои сокеты
        │
        └── DA Route Manager
              └── привилегированный helper
                    временные /32 и /128
```

Инварианты:

- выбор карты — один на всю программу;
- коннектор не выбирает карту и не делает fallback;
- все соединения одной операции используют один lease;
- ошибка одного соединения не влияет на остальные;
- loopback использует loopback;
- старые сессии не перепривязываются молча;
- DA-механизм не проникает в UA-транспорт.

## 5. UA Network Binding

### 5.1. Модель

- `AdapterId` — GUID.
- `AdapterInfo` — имя, состояние, адреса, prefix, gateway, ifindex, LUID, метрика, признак физического интерфейса.
- `AdapterSelection` — `Auto` или `Adapter(GUID)` + выбранный локальный IP.
- `NetworkLease` — снимок + generation.
- `SubnetSpec` — адрес, prefix, число адресов, диапазон; расчёт через `u64`.

### 5.2. Привязка

`BoundConnector` реализует `Connector` и `ConnectorBuilder`:

```text
TcpSocket::new_v4()/new_v6()
  → bind(local_ip)
  → IP_UNICAST_IF / IPV6_UNICAST_IF
  → connect(remote)
```

- Новый сокет на каждый `connect()`.
- Отдельный эфемерный локальный порт.
- IPv6 link-local — scope-id.
- Loopback — отдельная привязка.

Привязываются:

- `FindServers`, `FindServersOnNetwork`;
- `GetEndpoints`;
- создание и активация сессии;
- чтение, запись, browse, подписки;
- реконнекты;
- сканирование;
- mDNS.

Сессия создаётся через публичный API `async-opcua 0.19`:

```text
Client::session_builder()
  .with_endpoints(client.get_server_endpoints_from_url(bound_connector).await?)
  .with_connector(BoundConnectionSource::new(lease))
  .connect_to_matching_endpoint(description)?
  .user_identity_token(identity)
  .build(client.certificate_store().clone())
```

Текущий код уже создаёт отдельный `Client` и event loop на сессию
(`src/bff/ua.rs:1541`, `1619`); меняется только транспортная фабрика.

### 5.3. N+1

Правило:

```text
1. 127.0.0.1
2. ::1, если IPv6
3. локальный IP выбранной карты
4. N адресов подсети
```

- Loopback запускается первым независимо от подсети.
- Локальный IP — вторым.
- Остальные адреса — FIFO.
- До 32 одновременных проверок.
- TCP connect + UA handshake + `GetEndpoints` в одном соединении.
- Открытый TCP-порт без UA не считается результатом.
- Дедупликация адресов.
- Остановка сохраняет частичные результаты.
- Сканер не блокирует N сессий.
- 32 проверки сканера не входят в лимит 100 сессий.

Ограничения диапазона:

- обычные маски — без network/broadcast;
- `/31` — оба адреса;
- `/32` — один;
- APIPA — низкий приоритет;
- IPv6 — без перебора `/64`;
- до 4096 адресов — обычный запуск;
- больше — подтверждение и выбор более узкого CIDR;
- без молчаливого сужения маски.

DNS:

- используется системный;
- TCP-соединение всё равно привязано;
- если адрес недоступен через выбранную карту — явная ошибка;
- mDNS использует `InterfaceIndex`.

### 5.4. Лимит 100 UA-сессий

- `MAX_UA_SESSIONS: usize = 100` в `src/constants.rs`.
- Проверка в центральной точке создания UA-сессии.
- Считаются все UA `SessionView`, включая скрытые и отключённые.
- Удаление сессии освобождает слот.
- Реконнект существующей сессии разрешён.
- При 100 — локализованная ошибка, новая сессия не создаётся.
- DA-сессии в лимит не входят.
- Тест: 99 → 100 разрешено, 101 — отказ.

## 6. LDS/mDNS

### 6.1. LDS

- `FindServers` и `FindServersOnNetwork` через привязанный коннектор.
- Пустой ответ — не жёсткая ошибка.
- Дедупликация по `ApplicationUri` + endpoint.

### 6.2. mDNS

- `DnsServiceBrowse` / `DnsServiceResolve` для `_opcua-tcp._tcp.local`.
- `InterfaceIndex` выбранной карты.
- SRV/TXT → discovery URL.
- Окно сбора 5 секунд.
- Проверка найденного URL через `GetEndpoints`.
- Отдельный модуль, системный API Windows.

## 7. DA: полная реализация

### 7.1. Принцип

Для нативного DA/DCOM нет API привязки COM-соединения к карте.
Используется временный host-маршрут через выбранный интерфейс.
Это единственный практичный механизм, который действительно меняет путь DCOM-трафика.

### 7.2. Компоненты

1. **`DaRouteManager` в приложении**
   - разрешает DA-хост в IP;
   - проверяет текущий маршрут;
   - запрашивает helper;
   - ведёт refcount по `(IP, adapter GUID)`;
   - освобождает маршруты.

2. **`opcda-nethelper`**
   - отдельный crate `nethelper/` в workspace;
   - минимальные зависимости: `windows`, `serde`, `serde_json`;
   - манифест `requireAdministrator`;
   - 32-битная сборка вместе с приложением;
   - запуск по требованию, без постоянной службы.

### 7.3. Поток подключения DA

```text
resolve DA host
  → loopback/local? DA без маршрута
  → для каждого IP:
      маршрут уже через выбранную карту?
        → использовать, helper не нужен
      маршрута нет?
        → helper добавляет /32 или /128
      маршрут через другую карту?
        → ошибка конфликта, не перезаписывать
  → проверить GetBestRoute2
  → подключить DA-сессию
  → держать lease, пока есть сессии
  → освободить после последней
```

### 7.4. Параметры маршрута

- IPv4 `/32`, IPv6 `/128`.
- `InterfaceLuid` выбранной карты.
- Next hop:
  - on-link — `0.0.0.0` / `::`;
  - через шлюз — gateway выбранной карты.
- Finite lifetime + периодическое обновление.
- Неперсистентный маршрут.
- Конкретность `/32` важнее метрики.

### 7.5. Конфликты

- Существующий `/32` через другую карту не удаляется и не перезаписывается.
- Пользователь получает ошибку с объяснением.
- Если старая DA-сессия держит маршрут через прежнюю карту, новая сессия
  к тому же хосту через новую карту невозможна до отключения старой.
- UI предупреждает.
- Несколько DA-сессий к одному хосту используют один маршрут через refcount.

### 7.6. Helper: безопасность и жизненный цикл

- Запуск через UAC, один раз за запуск приложения.
- Named pipe:
  - только текущий пользователь;
  - случайное имя;
  - одноразовый токен;
  - проверка PID/SID клиента;
  - версия протокола.
- Helper принимает только:
  - добавление/удаление host-маршрута;
  - target IP, interface GUID/LUID;
  - без default route, multicast, broadcast;
  - prefix строго `/32` или `/128`.
- Audit log действий.
- При закрытии pipe удаляет созданные маршруты.
- При падении helper маршруты истекают по lifetime.
- При отказе UAC:
  - DA разрешён только если маршрут уже идёт через выбранную карту;
  - иначе явная ошибка, без молчаливого использования другой карты.

### 7.7. Ограничения DA

- Маршрут действует на весь компьютер для этого IP.
- DCOM может использовать дополнительные адреса; маршрутизируются все
  адреса, в которые разрешился хост.
- Текущая реализация DA — синхронный polling без `IOPCDataCallback`.
  Обратные асинхронные вызовы сервера в будущем потребуют отдельного решения.
- WFP-драйвер не используется.

## 9. Контракты и события

- Новые команды:
  - LDS/mDNS discovery;
  - старт сканирования;
  - остановка сканирования.
- `NetworkBindingSpec` передаётся в командах discovery/scan/connect.

- Потоковые события:
  - `Started`;
  - `Progress`;
  - `Found`;
  - `Finished`;
  - `Cancelled`;
  - `Failed`.
- `request_id` активен до терминального события.
- Поздние события предыдущего поиска отбрасываются.
- Отмена кооперативная: новые адреса не выдаются, текущим запросам даётся время на закрытие.

## 13. Критерии готовности

- Карта выбирается вручную, сохраняется по GUID, переживает перезапуск.
- Fallback — только физический адаптер, предпочтение не затирается.
- «Поиск через LDS/mDNS» работает штатными механизмами.
- «Поиск в сети»: loopback первым, затем N адресов подсети.
- Все UA-соединения привязаны к выбранной карте; подтверждено таблицей TCP.
- N сессий работают одновременно, сканер их не блокирует.
- 100 UA-сессий — единая константа, 101-я отклоняется.
- Большие маски не сужаются молча.
- DA-трафик к целевому хосту идёт через выбранную карту при доступном helper.
- Конфликты маршрутов и отказ UAC дают явную ошибку, а не тихий обход.
- Артефакты release включают приложение и helper.
- Все тесты и release-сборка зелёные.

## 14. Риски

- Маршрут DA действует на другие программы к тому же IP.
- DCOM может использовать дополнительные адреса; покрываются только
  разрешённые адреса хоста.
- Асинхронные DA-подписки с обратными вызовами потребуют отдельного механизма.
- Системный DNS не привязан к карте; гарантия относится к TCP-соединению.
- Helper требует UAC; без него DA разрешается только при уже правильном маршруте.
- Live DA-проверка ограничена доступным стендом.

## 15. Соответствие архитектурным правилам

**Class:** выбор карты — вышестоящая политика; UA binding, LDS/mDNS, сканер и DA route steering — разные классы ниже.

**Inv:** один lease на операцию; loopback первым; 100 UA-сессий; 32 проверки; отсутствие молчаливого fallback и сужения; cleanup маршрутов.

**N+1:** новый источник discovery или транспорт использует общую фабрику lease и существующие события прогресса/отмены; DA-механизм не проникает в UA.
